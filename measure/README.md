# 측정 체계 — MBO 실측용

'26년 임원 MBO의 두 지표를 증명하기 위한 기록 체계다. 배점이 가장 큰 두 항목이고, **10/31까지 As-Is 대비 개선을 숫자로 보여야** 한다.

| 지표 | 목표 | 배점 |
|---|---|---|
| 이벤트 발생 후 보고까지 리드타임 | 50% 단축 | 6 |
| 정보 자동 수집률 | 70% 이상 | 4 |

측정은 두 갈래로 이뤄진다.

1. **사람 기록** (`baseline-template.csv`) — 권역 담당자가 직접 남기는 As-Is 실측. 9월 말 ~ 10월 초 2주면 베이스라인이 나온다.
2. **에이전트 자동 기록** (`metrics/YYYY-MM-DD.json`) — 뉴스·공고 수집 에이전트가 매일 자동으로 남기는 값. 사람 손이 가지 않는다.

## 1. 사람 기록 — 쓰는 법

`baseline-template.csv`를 권역별로 복사해 쓴다(예: `baseline-북미-김OO.csv`). 엑셀에서 바로 열린다.
**정보 하나를 접할 때마다 한 줄**, 2분이면 된다. 완벽하게 적으려 하지 말고 빈칸은 비워 둔다.

| 열 | 뜻 | 예시 |
|---|---|---|
| `기록자` | 이름 | 김OO |
| `권역` | 북미 / 유럽 / 아시아 / 중동 | 유럽 |
| `대상` | 사업·발주처·기회 이름 | 체코 두코바니 |
| `정보종류` | 입찰공고 / 발주처동향 / 경쟁사 / 정책규제 / 기술 / 기타 | 입찰공고 |
| `발생일시` | 그 정보가 **세상에 나온** 시각 (공고 게시일, 기사 게재일) | 2026-10-05 09:00 |
| `인지일시` | 내가 **처음 알게 된** 시각 | 2026-10-08 14:30 |
| `기록완료일시` | 파이프라인 양식에 **입력을 마친** 시각 | 2026-10-09 10:00 |
| `보고반영일시` | 팀장·경영진 보고에 **반영된** 시각 | 2026-10-12 09:00 |
| `수집경로` | 메일 / 뉴스 / 공고사이트 / 인적네트워크 / 내부공유 / 에이전트 | 공고사이트 |
| `자동채움_항목수` | 시스템이 채워준 항목 수 | 0 |
| `수기입력_항목수` | 직접 입력한 항목 수 | 12 |
| `소요시간_분` | 이 건에 쓴 시간 | 25 |
| `비고` | 막혔던 점, 재입력 여부 등 | 통화환산 재작업 |

## 2. 계산식

- **리드타임(일)** = `보고반영일시` − `발생일시`
  - 중간값을 쓴다. 평균은 한두 건에 휘둘린다.
  - As-Is 기준값은 2주 기록의 중간값. 목표는 그 절반.
- **자동 수집률(%)** = `자동채움_항목수` ÷ **12** (파이프라인 표준 항목 수)
  - **분모 확정(2026-09-23)**: 표준 12항목으로 고정. 목록·구분은 [`standard-items.md`](standard-items.md) 참고.
  - 사실 수집 10항목은 에이전트 자동, 판단 2항목(시사점·제안대응)은 사람 확정(수기)이나 분모에는 포함한다.
  - 시스템 기준 현재값 = 10/12 ≈ 83%. 현장 CSV 실측이 모이면 그 중간값으로 갱신한다.
  - 어떤 항목이 애초에 없는 건은 그 항목을 분모에서 빼고 실제 표준 항목 수로 나눈다.

## 3. 에이전트 자동 기록

에이전트가 매일 `metrics/YYYY-MM-DD.json`을 남긴다. 사람 기록과 달리 손이 가지 않는다.

- `detection_lag_hours` — 기사·공고가 **게재된 시각부터 에이전트가 잡아낸 시각까지**. 리드타임 앞단의 실측값이다.
- `articles` / `by_region` — 처리 건수
- `sources_ok` / `sources_failed` — 접근 실패한 출처 (수집률 하락 원인 추적)
- `run_minutes` — 처리 시간 (MBO의 "처리시간 측정" 항목)

## 4. 주의

- 기록을 위해 일을 더 하지 않는다. 평소대로 일하고 시각만 남긴다.
- 빠뜨린 날이 있어도 괜찮다. 2주 중 절반만 채워도 중간값은 나온다.
- 개인 평가 자료가 아니다. 프로세스를 재는 것이지 사람을 재는 것이 아니다.
